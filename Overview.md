# Eclipse Common Lisp — System Overview

Eclipse Common Lisp is an ANSI Common Lisp implementation written by
Howard Stearns at Elwood Corp and now maintained by Blake McBride. It
provides an interactive interpreter (REPL) and a Lisp-to-C compiler.
It is unrelated to the Eclipse Java IDE. License: BSD 2-Clause.

## Architecture

The system is written mostly in Lisp. Most of the C runtime is
**generated** from it:

```
lisp/*.lisp  ──(Eclipse compiler, run in a host Lisp)──►  c/*.c  ──gcc──►  libeclipse.a / libeclipsed.a / eclipse
```

- **Generated C**: most files in `c/` (e.g. `kernel.c`, `list.c`) are
  output of the Eclipse compiler. Their headers say
  "Generated by Eclipse Common Lisp". Each one pairs with a
  `lisp/<name>.lisp` source.
- **Hand-written C**: `eclipse.h` (object model, macros, calling
  conventions), `interface.c` (primitives), `eclipse.c` (`main()`),
  `initd.c`, `statics-*.c`, `static-class.c` and `chars.c`.
- **Garbage collection**: the Boehm-Demers-Weiser conservative GC
  (`libgc`), which is an external dependency.

### Object model and calling convention (`c/eclipse.h`)

- Every Lisp value is a single C type, `clObject`, which is one machine
  word (`clWord`). The 32/64-bit choice is made in `eclipse.h`.
- Lisp names map to C names: `SYMBOL-VALUE` → `clSymbolValue`.
- Public functions take `clObject` arguments followed by an `clEOA`
  terminator. They check types and can return multiple values.
- `_cl`-prefixed versions are fast internal versions. They skip type
  checks, return a single value, may take raw C values, and may be
  macros.
- Closures, multiple values, the dynamic environment and non-local
  exits are built from macros in `eclipse.h`, using `setjmp`/`longjmp`.

## Libraries

| Output          | Contents |
|-----------------|----------|
| `libeclipse.a`  | Runtime: types, CLOS/MOP, lists, sequences, numbers, streams, reader, printer, format, packages, conditions, pathnames, files |
| `libeclipsed.a` | Development environment: the compiler (`*-comp`), code walker, interpreter (`evaluation`), `loop`, debugger, describer, pretty-printer defaults |
| `eclipse`       | REPL executable that links both libraries plus `-lgc -lm -ldl` |

## Build phases (`lisp/build.lisp`)

The Lisp sources are grouped so the system can bootstrap itself.
`run*` groups are runtime code and `dev*` groups are compiler and
development code:

| Group    | Examples |
|----------|----------|
| run0/dev0 | `common`, `parameters`, `mop-init`, `common-comp` (loaded into the host Lisp) |
| dev1     | Core compiler: `prog-comp`, `cont-comp`, `macro`, `clos-comp`, … |
| run1     | Kernel, types, symbols, classes, CLOS runtime, MOP, methods |
| run1a    | Generic functions, predicates, arithmetic, hash tables, sequences, arrays, strings, structs |
| run1b/dev2 | Environments, struct/condition compilation |
| run2     | Conditions, packages, bignums, streams, `init` |
| run3     | Reader, printer, pretty-printer, `format`, pathnames, files |
| dev3/dev4 | `loop`, format directives, debugger, describer, walker, interpreter, C back end (`c`, `c-walk`, `file-walk`) |

`*features*` controls how code is read in each context.
`:machine-compile` means Eclipse source is being compiled to C, and
`:lisp-host` means Eclipse code is running inside another Lisp.

## Execution model

How Eclipse compares with the usual ways Lisp systems run code:

| Capability | Eclipse |
|------------|---------|
| Pure interpreter | **Yes.** `eval`, `load` and the REPL run source forms through the code walker (`walk`, in `walk-top.lisp`/`walk-special.lisp`), which is the same walker the compiler uses. A `defun` typed at the REPL or loaded from source creates an `interpreted-function` that holds the lambda form and its lexical environment. Each call walks that source again (`interpreted-call` → `walk-lambda`). |
| Internal P-code / byte code | **No.** Forms are not translated into an intermediate code before they run. A byte-code back end (`byte-compiled-function`, `:byte`/`:bin` output formats, `lisp/non-build/byte.lisp`) was planned but never finished. In-memory `compile` does not produce byte code or native code. The function it returns is still run by the interpreter. |
| FASL files | **No.** `compile-file` cannot write a binary format, and `load` only reads source files. |
| Save/restore images | **No.** There is no `save-lisp`/dump-image facility. Each run of the `eclipse` executable starts from the initialized state built into the C libraries. Application code is either loaded from source or linked in as compiled C. |
| Stand-alone executables | **Yes, by linking.** The `eclipse` executable is a normal native program built from `eclipse.c` plus `libeclipse.a`, `libeclipsed.a` and `libgc`. Replace `main()` in `eclipse.c` to make an application that doesn't start the REPL. |
| Stand-alone executable via C | **Yes. This is the main compilation path.** See below. |

### Compiling through C

1. `(compile-file "foo" 'output-format :c)` writes `foo.c`. That file
   contains ordinary C that calls the runtime (`clCons`, `_clCar`, …),
   plus an init function named `usrFoo` that registers the compiled
   definitions.
2. Add `usrFoo()` to `main()` in `c/eclipse.c`, after
   `clInit()`/`clInitD()`, and set `USERSOURCE = foo.c` in
   `c/makefile`.
3. Run `make`. The resulting executable has `foo`'s functions built in
   as native machine code, and no Lisp source is needed at run time.
   Compiled and interpreted functions can call each other freely.

The Eclipse runtime itself is built the same way: its Lisp source was
compiled to the C files in `c/`. See `Compiler.md` for details,
including examples of custom `main()` programs and multi-file
applications.

## Directory layout

```
c/               C runtime (generated + hand-written), makefile
lisp/            Lisp source of the whole system; build.lisp
lisp/test/       Test suite (tests.lsp is the main configuration)
lisp/non-build/  Unbuilt/experimental modules (threads, byte compiler, walkers)
lisp/present/    Presentation system
doc/             HTML documentation (doc/eclipse/eclipse.htm)
bin/             Legacy precompiled binaries by platform
```

## Building

```bash
cd c
make          # eclipse, libeclipse.a, libeclipsed.a
make test     # build and test
make setup    # install to /usr/local
make clean    # remove build products
```

Requirements: GCC, GNU Make, libgc. Type `:exit` to leave the REPL.

## Status and limitations

- Primary platform: 64-bit Linux. Earlier releases ran on 32-bit Linux,
  macOS, Windows, HP-UX and Solaris.
- Single-threaded. Fixnums are 29 bits. `ed` is not implemented.
- The C code uses K&R-style function definitions.
- See `ISSUES.txt` for the current list of open items.
